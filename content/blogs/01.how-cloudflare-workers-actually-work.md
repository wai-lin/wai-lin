> I deployed a Worker that silently dropped requests. The bug was a single `void`.

Cloudflare Workers look like Node.js. Same JavaScript, same async/await, same fetch API. But they are fundamentally different; and if you do not understand why, your code will break in ways that do not make sense.

## V8 isolates, not containers

Traditional servers run in containers or virtual machines. A long-lived process with shared memory, persistent state, and a garbage collector that runs on its own schedule. When you start a Node.js server, it stays alive until you kill it.

Workers are different. They run on **V8 isolates**. These are isolated, lightweight execution contexts that share nothing with each other. There is no file system. No persistent memory between requests. No background threads.

Each request gets its own execution context. When the request finishes, the isolate can be reclaimed. Your Worker is not a server. It is a function that runs in a sandbox that forgets you existed the moment it returns.

This has consequences. Global variables do not persist across requests. `setTimeout` does not survive beyond the request lifecycle. There is no "background" the isolate is the foreground and the background simultaneously.

## The event loop works the same (sort of)

The JavaScript event loop in Workers is the same one you already know. Microtasks, macrotasks, `queueMicrotask`, `setTimeout` all familiar.

But there is a catch: the event loop only lives as long as the request. When the fetch handler returns, the runtime does not wait for pending microtasks or unhandled promises.

In Node.js, an unhandled promise rejection logs a warning and the process stays alive. In Workers, the isolate is destroyed. The promise never resolves, never rejects, never logs anything. It vanishes.

This is why `void` is dangerous. You are telling the runtime "I do not care about this" and the runtime agrees, it drops it.

## `void` vs `await` the gotcha

The `void` operator evaluates an expression and returns `undefined`. It does not cancel the promise, stop execution, or suppress errors. It just tells the runtime "do not wait for this."

`await` pauses execution until the promise settles. If it rejects, the error propagates. You can catch it, retry it, log it.

The difference matters everywhere, but it matters most in Workers because:

1. There is no process to keep the runtime alive after the handler returns
2. Unhandled rejections do not log anywhere they vanish
3. Background work that is not awaited may never complete

| Behavior                             | `void promise`         | `await promise`           |
| ------------------------------------ | ---------------------- | ------------------------- |
| Execution continues immediately      | Yes                    | No, pauses                |
| Errors are caught                    | No                     | Yes, with try/catch       |
| Promise completes if handler returns | No (isolate destroyed) | Yes                       |
| Suitable for critical writes         | No                     | Yes                       |
| Suitable for fire-and-forget         | Dangerous in Workers   | Overkill for non-critical |

The `void` operator does not mean "run this in the background." There is no background. The work either completes before the handler returns, or it does not complete at all.

## Code comparison

### The broken Worker `void` on critical path

```ts [worker.ts]
export default {
	async fetch(request, env) {
		const data = await request.json();

		// Fire and forget: if this fails, we never know
		void env.DB.prepare("INSERT INTO logs (?)").bind(JSON.stringify(data)).run();

		return new Response("OK");
	},
};
```

The database write starts, but there is no guarantee it finishes. When the handler returns `new Response("OK")`, the isolate can be destroyed at any moment. The promise is dropped. The data is lost.

### The fixed Worker `await` with error handling

```ts [worker.ts]
export default {
	async fetch(request, env) {
		const data = await request.json();

		try {
			await env.DB.prepare("INSERT INTO logs (?)").bind(JSON.stringify(data)).run();
			return new Response("OK");
		} catch (err) {
			return new Response("Failed to log", { status: 500 });
		}
	},
};
```

The database write completes before the response is sent. If it fails, we catch the error and respond accordingly. The user knows what happened.

### The webhook problem when you need both

This came up building a Messenger bot. Facebook requires a 200 response within 5 seconds. If you `await` the database write before responding, you risk timeouts. If you `void` it, the write silently fails.

```ts [webhook.ts]
export default {
	async fetch(request, env) {
		const webhook = await request.json();

		// Save raw webhook but Worker closes before this finishes
		void env.DB.prepare("INSERT INTO raw_webhooks (?)").bind(JSON.stringify(webhook)).run();

		// Reply to Facebook instantly
		return new Response("OK", { status: 200 });
	},
};
```

The Worker returns `OK` to Facebook, then the isolate is destroyed. The `void` promise never completes. All the background calculations are lost.

### The fix `waitUntil` for non-critical work

Cloudflare provides `ctx.waitUntil(promise)` to extend the Worker's lifetime after the response is sent:

```ts [webhook.ts]
export default {
	async fetch(request, env, ctx) {
		const webhook = await request.json();

		// waitUntil keeps the isolate alive for this promise
		ctx.waitUntil(
			env.DB.prepare("INSERT INTO raw_webhooks (?)").bind(JSON.stringify(webhook)).run(),
		);

		// Reply to Facebook instantly
		return new Response("OK", { status: 200 });
	},
};
```

`waitUntil` works for fast operations cache writes, analytics pings, logging. But it has a **30-second hard timeout**. If the promise has not settled after 30 seconds, it is canceled. For heavier processing, you need a different architecture.

### When 30 seconds is not enough, use Queues

For work that must complete reliably, use Cloudflare Queues:

```ts [webhook.ts]
export default {
	async fetch(request, env, ctx) {
		const webhook = await request.json();

		// Send to queue for guaranteed processing
		ctx.waitUntil(env.WEBHOOK_QUEUE.send(webhook));

		// Reply to Facebook instantly
		return new Response("OK", { status: 200 });
	},
};
```

Queues provide guaranteed delivery, automatic retries, and dead letter queues. The processing happens in a separate consumer Worker, not in the request path.

## Practical guidelines

| Use `await` when...               | Use `waitUntil` when... | Use Queues when...                  |
| --------------------------------- | ----------------------- | ----------------------------------- |
| Writing to a database             | Cache warming           | Processing exceeds 30s              |
| Sending a webhook response        | Analytics pings         | Guaranteed delivery needed          |
| Updating user state               | Non-critical logging    | Retries matter                      |
| Any operation the user depends on | Fast operations (< 30s) | Decoupling response from processing |

**Rule of thumb:** `await` everything by default. Only skip `await` when you have consciously decided the work can be lost and verify that `waitUntil` actually completes for your use case.

**Common mistake:** Developers coming from Node.js assume background work "just works." In Workers, there is no background. Every promise either completes before the handler returns, or it does not complete at all.

## Conclusion

The bug was a `void` on a database write. The Worker closed before it finished. The fix was `await` but the deeper lesson is understanding that Workers do not have a "background."
